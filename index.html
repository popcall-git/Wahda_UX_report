2导航与信息架构

这是本次改动中最结构性的一类——不改变任何单个页面的长相，但改变了用户到达每个页面的路径长度。

更新点 原设计 现设计 设计逻辑
底部导航 5 Tab 平铺占满（Discover / Places / Chats / Feeds / My Hub） 4 Tab + 中央固定 FAB（Feeds / Places / ◉ / Chats / My Hub） ① 4 个 Tab 宽度舒展，触控目标不再压缩；② FAB 给「创作」一个固定心智锚点，任意页面可达；③ 留出 Live / 小程序 / 游戏的扩展挂载位，避免未来再挤 Tab
通知体系 全站通知集中在 Discover 右上角铃铛，其他 Tab 零提示 Tab 级未读红点（Places 圆点 / Chats 数字角标）＋ 聚合通知中心（内容 / 系统 / 社交分组） 通知的价值在于「在用户所在处告诉他」。集中式入口要求用户先主动想起去看，分布式角标则是被动推送；两者叠加，兼顾实时性与归档需求
Wallet 入口 Hub → Settings → Wallet → Top Up，4 层逐层跳转，且无余额预览 Hub 首屏 Wallet 卡片，1 层直达，内嵌余额与 Top Up / Withdraw 快捷操作 凡是「资产」都必须是「抬眼可见」。深层入口会让用户无法形成余额感知，进而抑制充值、提现、转账等一系列后续动作
返回语义 深层页只能逐层 pop，无跳级返回 页面栈按层级管理，弹层与页面分离，深层操作完成后一次返回目标层 返回的语义应该是「回到我要去的地方」，而不是「撤销我走过的一步」。逐层 pop 把导航成本转嫁给了用户
小程序架构与入口 无 小程序在下拉菜单一级可达；常用 / 收藏 / 汇聚页 入口层级决定使用频率：藏在面板里的小程序不会被想起。一级可达让小程序成为主页面的自然延伸；三层结构按使用频率组织——常用的直达、收藏的固定、汇聚页承载完整目录与发现

3新用户转化路径

注册流程的改动不是「少填几个字段」，而是把收集信息的时机从「进入之前」挪到了「需要之时」。这是转化率层面影响最大的一类改动。

更新点 原设计 现设计 设计逻辑
注册门槛 手机号验证 → 邮箱 / 姓 / 名 / 昵称 / 密码，全部填完才能进 App 选验证方式（手机标 Fastest）→ 输入 OTP → 直接进入 App 每一步强制填写都在叠加流失概率。用户此时还没有获得任何产品价值，却要先付出完整的隐私成本——这违背了「先给价值、再收信息」的基本顺序
资料完善 一次性强制表单，中途退出即丢失进度 进入 App 后按需补充；表单草稿本地保留，退出重进不丢 把「一次性大决策」拆成「多次小决策」。用户对每个字段的心理成本是独立的，分批交付能显著降低单次抗拒
登录与注册分流 未区分老用户路径，登录入口不明显 欢迎页双入口：Get Started（新用户）+ 已有账号登录；登录页支持手机/邮箱 + 密码切换与 OTP 老用户被塞进新用户流程是常见的隐性流失点。分流后，两条路径各自只需要回答一个问题
注册后引导 注册完成即进入空首页，无推荐 完成页后接入推荐关注，帮助用户快速建立信息流 新用户首屏是否「有内容」，直接决定他是否在第二天回来。空信息流是新产品的第一号杀手
游客模式 — 登录页第三入口「以游客身份进入」；可自由浏览 For You 信息流、Places、个人主页与活动详情；触发关注 / 点赞 / 评论 / 收藏 / 转发 / 报名 / 发帖或 Messages / Hub / 通知等需要账号的动作时弹出注册引导，注册完成自动回到原位 游客模式把「获得价值」挪到了「验证身份」之前，封住了漏斗上最后一个未封口的环节；注册引导出现在用户意愿最强的那一刻，而不是入口处
Onboarding 偏好采集 Onboarding 无偏好采集环节，个性化推荐缺少冷启动数据来源 新用户 onboarding 根据新用户 Recommendation 的结果采集 preference，作为个性化推荐数据的启动来源 冷启动决定推荐质量的上限；在用户表达意愿最强的时刻采集偏好，比事后猜测更准确

游客模式

  • 说明：登录 / 注册页新增「以游客身份进入」第三入口，与 Fast Login 并列。游客可自由浏览 For You 信息流、Places、个人主页与活动详情；触达需要账号的动作（关注 / 点赞 / 评论 / 收藏 / 转发 / 报名 / 发帖开播 / Messages / Hub / 通知）即弹出注册引导，注册后自动回到原位；游客态隐藏 Following / Community 分栏与消息角标。
  • 目标：把「获得价值」挪到「验证身份」之前，封住漏斗最后一个未封口的环节；注册时点从「入口处强制」改为「意愿最强时引导」。
  • 价值：犹豫型与隐私敏感用户零门槛试用；消除「注册完发现没内容」的空流失；注册完成率与次日留存受益；与 Fast Login 互补——一个降注册成本，一个降进入成本。

4钱包与金融

钱包与金融模块是设计判断最密集的一类，要同时满足用户理解成本和教义合规。

更新点 原设计 现设计 性质
充值 Top Up 5 档固定套餐（Starter / Basic / Silver / Gold / Diamond），仅 Silver 标 Best Value，但按 Coin/$ 比例 Diamond 实际更划算——标签与事实矛盾 自由输入金额：法币与金额同框 → 收款项平行展示 → 汇率与手续费置于卡外左下 → 四种支付方式（本地钱包 / 卡 / Google Pay·Apple Pay / P2P 市场） 重构
提现 Withdraw 入口带 Creator 角标（个人账号看不到完整入口，且无升级说明）；服务费在进入页面前才告知 独立提现页：选币种 + 输金额 → 收款方式 Bank Transfer (SWIFT) → 脱敏展示已存银行卡（仅尾 4 位 + SWIFT 码）→ 可添加新卡（IBAN / SWIFT 校验）→ 10 USD 手续费与 0–3 工作日前置说明 → 提交 新增
授信 Manage Credit 无 滑杆在 0–最大授信额度之间调整，Save 后钱包信用数字联动更新，Cancel / 返回回到钱包 新增
P2P 转账 无独立 P2P 体系 P2P 转账 / 收款 / 转账记录 / 收款历史，接入钱包余额与交易流水 新增
钱包视觉 蓝色渐变卡，色值未规范，全站没有同色系呼应 品牌深色 hero 卡，余额单位统一为 Wahda Coins，展开明细与快捷操作 重构

为什么 Top Up 要拆成「卡内 / 卡外」两层

  • 卡内放决策：法币与金额同框输入，收款项平行展示——用户只需回答「充多少」，无需自行换算。
  • 卡外放解释：汇率（1 USD = 0.9 Coin）与手续费（0.10 USD）作为解释性信息置于卡片外左下——成本在输入金额之前已知。
  • 支付方式独立成步：本地钱包 / 银行卡 / Google Pay·Apple Pay / P2P 市场四选一，与金额决策分离，互不干扰。
  • 为什么分层：决策信息与解释信息混在一张卡里会互相抢注意力；拆成「卡内 / 卡外」两层后，界面只呈现用户当步需要的信息。
关于手续费前置
原设计的提现服务费（10,000 Coin + 200 fee）在进入页面前并不告知，属于隐式成本。现设计把「10 USD 手续费」与「0–3 个工作日到账」放在金额输入卡的正下方——用户在输入金额之前就已经知道成本。金融产品的透明度不是合规负担，而是信任资产：先告知成本，用户才会相信后面的数字。

5穆斯林工具与路径重构

对一款面向全球穆斯林的超级 App 来说，信仰不是「特色模块」，而是产品的默认前提。这类改动分两层：一层是让穆斯林工具变得可达，另一层是重构这些工具的到达路径。

更新点 原设计 现设计 设计逻辑
穆斯林工具入口 礼拜时间 / 朝向 / Halal 无一级入口，只能靠 Discover 搜索；而搜索算法未覆盖穆斯林工具 Feeds 顶部下拉唤出「Islamic Tools & Mini Apps」面板，穆斯林工具与小程序同层可达；Feeds 顶部固定 Prayer 时间提醒 把「搜索可得」升级为「穆斯林工具一级可达」。礼拜时间有明确的触发点，用户不会为了找入口而搜索——入口必须主动出现在他面前
Halal 认证与商业化 Halal 餐厅评价已成型，但缺少可信的认证标识；认证仅用于站内筛选与展示，无对外输出 Halal 认证标识前置到商户卡片与详情，作为可信度信号；认证数据积累后以 API 方式对外提供，作为商业化场景之一 对穆斯林用户来说，「Halal」不是一个筛选条件，而是一个准入条件——标识的价值在于「让我不需要自己判断」；认证数据积累后具备外部价值，API 输出让合规能力从成本项变为收入项

6社交与内容

这一类的共同主题是「把数字还原成人」。原设计里很多社交信号只有计数，看不到关系链——而社交产品的价值恰恰在于关系链本身。

更新点 原设计 现设计 性质
Feed 互动者 操作栏只有计数（12 Likes、3 Reposts），看不到是谁，无法点击头像直达主页 详情页展示点赞者头像堆叠 + 姓名列表（「Ahmad, Fatima + 7 others」），社交关系链可视化 重构
Feed 详情结构 内容与评论混在一页 Post / Comments / 互动者 分视图，各自有独立排序与操作 重构
直播 原设计未覆盖直播形态 直播间与观看页；好友正在直播时，Chats 列表行出现「正在直播」角标 新增
粉丝 / 关注列表 个人中心仅显示 1.2K followers / 318 following 数字，不可点击、无法查看 数字可点击进入 Followers & Followings 双 Tab 列表；关注状态与 Feeds 共用同一份关系数据，互关用户同时出现在两个列表 新增
群组体系 有 Community 概念但缺少完整管理能力 建群、群资料、成员列表、权限设置、邀请、移出成员、群二维码、群内搜索、公告 新增
聊天协作 消息请求有计数器，但会话级工具缺失 会话设置、隐私设置、聊天主题、屏蔽、联系人管理 新增
社交发现 Events、Community 依赖 Discover 聚合页，靠用户主动检索 Events、Community 等社交场景从聚合页面转向跟随社交关系：结合社交链、Location 与个性化推荐 新增
直播发现与预告 直播入口单一，无预告机制 聚合页 + 分类推荐（Feeds 流、Posts、用户 Profile、Chats）；分「进行中 + 预告」两个场景，用户可对预告设置 Remind 新增
预设广告入口 广告位未预设，无场景化推荐 预设广告入口，在不同场景进行分类推荐（结合 Feeds、Places、Events） 新增
Follow 与 Contacts 界限 两者概念混用，关系类型的语义不清 定义清楚界限：Follow 不等于 Contacts——Follow 是用户自主单向，Contacts 是建立双向社交关系 新增
Chat 好友直播状态 会话列表不展示好友开播状态 Chat 里增加好友状态：正在直播，或正在开放直播间，可一键跟随进入 新增

7创作、账号与扩展能力

这一类回答的是「超级 App 怎么长大」——把创作收敛到一个中枢，把外部能力挂到宿主层，把身份分层管理。

更新点 原设计 现设计 设计逻辑
创作入口 单个悬浮「+」，点入后弹出四选项（Post / Community / Event / MyStore） 底部中央固定 FAB 唤出 Creation Hub，四类能力按语义分组，并可按类型补足各 Tab 内的情境化快捷入口 「+」是位置，不是功能。用户点击前的疑问是「我要做什么」，而不是「我要点哪里」。因此入口需要先回答内容类型，再回答动作。固定 FAB 同时解决了「任意页面可发起」和「不占用 Tab」两个约束，同时解决了原有浮动按钮占用屏幕空间、用户总是需要把它挪到别的位置的问题
扫一扫 无 设置区放大入口 + 独立扫码页，覆盖三个场景：扫码收款、核销活动门票、扫码加好友 扫码是同一个动作，但背后的业务域完全不同（金融 / 票务 / 社交）。三场景合一会让用户不确定扫完会发生什么，因此结果必须可预期——由扫码后的落地页分别承接
小程序宿主 原设计未覆盖，但架构上需要预留 小程序宿主层页面，与 Islamic Tools 同层可达（顶部下拉面板） 超级 App 的扩展能力不能靠新增 Tab 实现——Tab 是稀缺资源（原设计已被 5 个占满）。挂到「下拉面板」这个次级入口，既保证可达又不挤占主导航
多账号体系 Personal / Creator / Professional 三层设计不完整，切换后无当前账号标识，路径与差异说明缺失 账号切换抽屉 + 各类型账号的门槛与权益说明，Creator 验证流程独立成页 用户不切换账号的原因通常不是「找不到入口」，而是「不知道切过去会怎样」。因此说明必须先于入口

8全局搜索与推荐

搜索从「一个页面里的功能」升级为「全局工具」：任何入口发起的搜索都命中同一份全量索引，而结果的排序优先级跟随入口场景变化；推荐侧则把多种内容类型混进同一条信息流。

更新点 原设计 现设计 设计逻辑
全局搜索 Discover 内单一搜索框，只覆盖局部内容；无分类搜索、无 Top 搜索、无搜索推荐 搜索升级为全局搜索，覆盖全量内容类目（用户 / 帖子 / 地点 / 活动 / 小程序 / 穆斯林工具等），支持分类搜索；增加 Top 搜索和搜索推荐 搜索是全局工具，入口却是局部的——原设计只能搜到局部内容，意图无法命中全量内容；升级后任意入口发起的搜索都指向同一份全量索引
按入口差异化排序 所有入口返回同一套排序结果，与用户所处页面无关 不同主页面入口采用差异化的搜索类目排序规则——同一关键词从不同入口进入，结果优先级随入口场景重排（如 Places 入口优先地点与活动，Discover 入口优先内容与用户） 入口即意图：用户在哪个页面发起搜索，决定了他在找什么。类目排序随场景变化，结果才与用户所处页面相关
多内容混合推荐 各板块内容独立分发，无跨类型混合推荐 支持多内容混合推荐——帖子、地点、活动、直播、小程序等按统一信息流混排；配合 Onboarding 偏好采集解决冷启动 超级 App 内容形态多样，单一类型推荐会埋没其他板块的内容供给；混排让每个板块的内容都有被发现路径，也延长 Feed 的消费时长
